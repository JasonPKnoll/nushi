# 0132. Terminals on Windows run on ConPTY

Status: accepted, 2026-11-16. Amends [0124](0124-the-daemon-builds-on-windows.md) (the daemon on Windows) and [0098](0098-the-daemon-runs-a-folders-dev-servers.md) (a dev server's stop).

## Context
A terminal beside a chat, and a dev server's program, run on one of the daemon's pseudo-terminals (`internal/terminal`): on Unix a pty device, the program in a session and process group of its own, what runs on it found by its controlling terminal, Close a SIGHUP to all of it. Windows has none of that. Its pseudo-terminal is ConPTY's pseudo-console (`CreatePseudoConsole`): two pipes, one the program reads and one it writes, and a console host between them. Go's `os/exec` can't attach a program to one (`SysProcAttr` has no attribute list), Windows has no foreground process group or SIGHUP, and no login shell to start: so terminals refused to start there (ADR 0124), and proctree read no processes.

## Decision
- **The pseudo-terminal** is ConPTY's. `terminal.Start` makes the two pipes and the pseudo-console, and starts the program itself (`CreateProcess` with `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`) on the command line `os/exec` would use once `batchfile.Guard` has had its say (an npm shim runs as node and its script; the current folder is out of the program's search). Its standard handles are none, or it would get the daemon's own (its log) rather than the console's. The shared `Terminal` reads and writes through its `out` and `in` and waits on its `os.Process`; what each OS holds besides is its own (`sys`: the pty and its device on Unix; the pseudo-console, the job and the pipes on Windows).
- **A job holds the program's tree.** The program starts suspended, joins a job object that kills what's in it when it's closed, then runs: what it starts is in the job from the first instruction, which a tree read after the fact can't promise.
- **Close** closes the pseudo-console (what's attached gets `CTRL_CLOSE_EVENT`, as a closed console window sends), waits the same grace as Unix's SIGHUP, then ends the job with all that's left. The pseudo-console is closed too once the program exits: its output pipe doesn't end before.
- **Terminate** (a dev server's stop, ADR 0098's SIGTERM) is Ctrl+C typed on the terminal: ConPTY makes `\x03` the console's Ctrl+C event for what runs on it.
- **Ctrl+C reaches the program.** A process started in a process group of its own ignores Ctrl+C, and what it starts inherits that: the app starts the daemon so, so a shell the daemon started would ignore every Ctrl+C. The daemon turns Ctrl+C on in itself around the `CreateProcess` alone, under a lock, then puts its own flag back (read from its process parameters): the daemon stops on Ctrl+C (`os.Interrupt`), and must keep ignoring one on its hidden console; a daemon started from a terminal, which takes Ctrl+C, is left as it is.
- **The foreground program** is the newest process under the shell (proctree), the shell's own when it has none: Windows has no foreground process group. Its command line is the program's as the system keeps it.
- **The shell** is the one Windows Terminal's default profile opens, as a new tab there would: Windows has no login shell, and that's where a Windows user chooses theirs. The settings are read for each new terminal, JSON with comments: the profile's command line, else the one its source's fragment gives (Git for Windows's Git Bash, a WSL distribution's), else the system shell its fixed id names (Windows PowerShell, the Command Prompt), PowerShell 7 for its generator, `wsl.exe -d` for a WSL distribution; `%NAME%`s expanded. A profile Nushi can't start (Azure's Cloud Shell, Visual Studio's prompts), or no Windows Terminal, gives PowerShell 7 where it's installed, else Windows PowerShell. Reading the settings (`wtprofile.go`) is apart from finding them (`termshell_windows.go`), so CI's Mac and Linux jobs test it.
- **Its environment** is the agents' (the registry's, ADR 0126), not the daemon's: a Windows shell doesn't build one of its own at login as a Unix login shell does, and the daemon's is the app's from when it started.
- **proctree reads Windows's processes**: a Toolhelp snapshot for who started whom, `GetProcessTimes` for when, `NtQueryInformationProcess` for a command line, split as the program's C runtime would; a parent id naming a process that started after its child is an id used again, so the child has none. There are no process groups (`Pgid` 0): `StopGroup` stops none, and `Stop`'s SIGTERM has no counterpart, so its grace passes before `TerminateProcess`.

## Consequences
- A terminal, a dev server and a chat's `servers` tools work on Windows, and the app's terminal pane with them; the tab names the program running in it.
- Changing Windows Terminal's default profile changes Nushi's next terminal; a shell inside WSL is a Linux VM's, so its programs aren't Windows processes: no foreground program is named in it, and Close ends WSL's console client, which ends the shell.
- A program that ignores `CTRL_CLOSE_EVENT` is ended with the job after the grace, as one that ignores SIGHUP is killed on Unix.

## Alternatives considered
- A Nushi setting for the shell: Mac and Linux have none, following the user's own choice; on Windows that choice is Windows Terminal's.
- `%COMSPEC%` (cmd) as the shell: what every Windows has, but few choose it, and Windows Terminal's default is PowerShell.
- A pty library (`go-pty`, `conpty`): a dependency for the hundred lines `golang.org/x/sys/windows` already gives.
- The newest process on the terminal's console as the foreground program, by `GetConsoleProcessList`: the daemon would have to attach to each pseudo-console to ask, and the shell's tree is already read for its listing.
