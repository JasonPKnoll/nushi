# 0133. Windows reads listeners and memory, and binds a command to a job

Status: accepted, 2026-11-17. Amends [0124](0124-the-daemon-builds-on-windows.md) (the daemon on Windows: off were `listeners` and `footprint`, and a bound command had no job).

## Context
ADR 0124 left the daemon on Windows reading no processes: `listeners` and `footprint` answered `errors.ErrUnsupported`, so a dev server's port was never checked as its own or named when taken, and the app's memory card stayed off (the daemon's `GetMemory` answers `unimplemented`, and the app stops asking). It also left `procgroup.Bound`'s commands (git, gh, npm, an agent's `--version`, Claude's `mcp` commands) to `taskkill /T`, which follows each process's parent from the command down and so misses one whose parent ended first; `procgroup.Start`'s programs had a job object, but `Bound` sets up a command its caller then runs, and 0124 found no moment after the start to add it to one. `proctree` (Toolhelp's snapshot, a process's command line) comes with the terminals, apart from this.

## Decision
- **Listeners** come from iphlpapi's `GetExtendedTcpTable` (`TCP_TABLE_OWNER_PID_LISTENER`), IPv4's table and IPv6's, through `windows.NewLazySystemDLL` (no cgo), each row a listening socket, its local address and the pid that owns it; a buffer too small is grown and asked again. A row is kept when a connection to localhost can reach it (127.0.0.1, ::1 or a wildcard), as on the Mac and Linux. Windows lists a dual-stack socket (an IPv6 wildcard without `IPV6_V6ONLY`: Go's `":p"`, Node's default) in both tables, as 0.0.0.0:p and [::]:p, and tells no socket's `IPV6_V6ONLY` (seen on Windows 11 23H2, 2026-11-17, for Go's five kinds of listener), so a process's [::]:p beside its own 0.0.0.0:p is one dual-stack `Listener`: were they an IPv4 socket and a v6-only one, that one listener still takes what they take, each family's connections to that process. Each socket is listed once, with the process that opened it, not each holding it, and every user's sockets are listed (the table has them all; a service's on a wildcard is one a connection may reach). The parsing (`tcptable.go`) builds on every OS, so CI's Linux and Mac jobs test it.
- **Memory** is a process's private bytes (`GetProcessMemoryInfo`'s `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`, Task Manager's "Commit size"): what it alone holds, in RAM or paged out, as macOS's footprint counts what is compressed or swapped; shared pages (DLLs' code, a mapped file) aren't counted, so a tree's sum counts none twice. A process is opened with `PROCESS_QUERY_LIMITED_INFORMATION` alone; one that can't be (a service's, a protected process) reads 0. The process list is Toolhelp's snapshot. A Windows process keeps an ended parent's pid, which may since be another process's, so a process is its parent's child only when it started after it (`GetProcessTimes`), and one whose start can't be read is no one's; that also keeps a tree from looping. The app's memory card then shows on Windows with nothing of its own changed.
- **A bound command joins a job.** Go's `exec.Cmd` runs nothing of the caller's between starting the process and the caller's `Wait` but the copy of the command's input into its pipe, which it starts at once, in a goroutine. So on Windows `Bound` wraps `cmd.Stdin` (none becomes an input at its end at once) and that copy's first read puts the command in a kill-on-close job (`hold`, as `Start` does), a moment after it starts, as `Start`'s are; the context's end kills the job (`TerminateJobObject`), so a process whose parent ended first goes too, and before the command has joined, or without a job, its tree as before (`Kill`). Once the command exits by itself the job is let go of without killing what is left in it (its kill-on-close limit taken off, then closed), as a Unix group lives on after its leader: until then, a daemon that dies ends what the command started. A command given no input reads from an empty pipe rather than NUL. One whose input is a file (a `StdinPipe` taken before `Bound`) is handed that file with no copy, and keeps the tree's kill. So a command's input is set, or its `StdinPipe` taken, before `Bound`: git's `check-ignore`, `cat-file` and pathspec staging take an `unbound` command to do so, and Claude's `mcp_toggle` gets its two requests as a reader.

## Consequences
- In the app on Windows a dev server's identity check and the "port taken by …" note work as on the Mac (once `proctree` reads Windows's processes, which the check needs for the server's own), and the memory card shows the daemon's, the app's and each chat's.
- A List takes about 0.2 ms (2026-11-17, an i9-9900K, 455 processes, 132 listening sockets); a memory report, the snapshot and each process's start, about 16 ms.
- `listeners` and `footprint` join `procgroup` and the rest in CI's "Go on Windows" job. `listeners`' test of a child's listener in this process's tree skips on Windows until `proctree` reads processes there.
- A future `Bound` caller that sets `Stdin` after `Bound` gets no job on Windows (the tree's kill), and one that takes `StdinPipe` after it gets exec's "Stdin already set": `Bound`'s doc says so.

## Alternatives considered
- `NtQuerySystemInformation`'s process list for the snapshot (each process's parent, start and private bytes in one call, wrapped by x/sys): 25–36 ms here against Toolhelp's 13 ms with every process's start read, and its struct is the kernel's own, documented only in part.
- Private working set (`PROCESS_MEMORY_COUNTERS_EX2`, Task Manager's default column): newer than the rest of the struct, and memory paged out isn't counted, so a trimmed process would look small while it holds its memory.
- Starting a bound command suspended (`CREATE_SUSPENDED`) and resuming it once in the job: nothing races, but resuming needs the main thread's handle, which `os.Process` doesn't give (a thread snapshot or the undocumented `NtResumeProcess`), and a command whose input copy never ran would never start.
- Routing every bound command through procgroup's own runner (`procgroup.Output`, `Run`): no input wrapped, but each of the two dozen callers changes, and a new one that runs the command itself silently has no job.
- A placeholder process in each command's job as its parent (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, which passes on its job): a process more for every git call, and the command's handles would have to be passed through it.
- Killing what is left in the job when the command exits by itself: Unix doesn't, and a command may leave work running on purpose (git's `gc --auto` detaches on Unix).
